# Long festival days split the Live Activity into 8-hour segments

2026-11-13 产品决定：实时活动在开场前 3 小时出现，一直陪到散场。单个实时活动最多活跃 8 小时（平台上限），所以一天超过 8 小时的音乐节拆成几段，每段一个实时活动，前后接力。补充 ADR 0044。

- 覆盖范围：开场前 3 小时 → 当天散场。只拆有时刻表的音乐节日；普通现场仍只保留散场前最后 8 小时一段。
- 切法：从散场往前按 8 小时切，压轴所在的最后一段最长。例：12:00–23:00 → 09:00–15:00、15:00–23:00。
- 段身份记在 `ShowLiveActivityAttributes.segmentEnd`。旧版本创建的进行中活动没有这个字段，视为当天最后一段，升级后不重建；旧版本预约（pending）的活动带着旧 alert，重新预约。
- 交接（iOS 26+）：当前段和当天剩余各段同时预约（App 被强杀后不会被唤醒补预约）。系统激活预约段有数秒延迟，到点 60 秒内仍 pending 的段先等它激活，不结束重建；宽限期一过 App 再规划一次，仍未激活就重建。下一段到点由系统拉起，同时把已退出的 App 后台唤醒（2026-11-13 真机实测，约 3 秒）；App 启动时跑一次同步，结束上一段、把新一段的推送 token 交给云端计划。上一段的云端计划在交接时刻推一条 `endsActivity` 的 end，立即收起，防止没被唤醒时两段并存。
- pending 的活动开始前没有推送 token，所以下一段的计划只能在它开始后上报；在那之前，这一段的「想看」提醒留在本地通知。
- 预约启动必带 alert（系统要求，不能静默）：
  - 开场段的 alert 就是「快开场了」那条开场前提醒，文案与本地通知一致；被 8 小时上限截短时按实际剩余时间说。开场段预约成功后，本地开场前通知让出（`LiveActivityOpeningCoverage`，只认同一次开场，延期后的新开场照常走本地通知），开场标记仍保留，开场后不会补发。预约在开场前被撤销时交还本地通知。
  - 交接段的 alert 说正在演出的那一场（没人在演时说下一场），用无声音频，只亮屏不响。交接是技术边界，不是换场。

## Considered Options

- 单个活动只覆盖最后 8 小时。否决：11 小时的音乐节要开场 3 小时后才出现，不符合现场助手的定位。
- 从开场往后切。否决：最后一段可能很短，压轴时段反而落在短尾巴里。
- 只预约下一段，到点被唤醒时再预约后面的。否决：App 被强杀后不会被唤醒，第三段起就起不来。
- 服务端 push-to-start。否决：同样必带 alert，且要多存一份 token；系统预约已能后台唤醒 App。
- 实时活动 alert 与本地开场通知都保留。否决：同一时刻两条内容相同的提醒。

## Consequences

- 云端 `syncLiveActivityPlan` 保留步骤的 `endsActivity`，`dispatchLiveActivityPush` 据此发 end；服务端需先于 App 部署。旧服务端会把它当普通 update，上一段要等 App 被唤醒时收起。
- 60 秒后的重新规划只在 App 仍有执行时间时发生；后台唤醒后被挂起则等下次同步。
- 用户上划强杀 App 时系统不会后台唤醒，下一段停在预约时的内容，直到下次打开 App。
- 开场前通知不再带长按「播放」唱片和天气提示（由实时活动接管的那几场）。
