# 灵动岛与实时活动：场景、文案及布局评估

日期：2026-10-21  
代码基线：`682014f5`，`feat/live-activity-reminders`  
范围：普通演出、音乐节现场模式、想看提醒，以及前后台和异常情况下的显示。

## 结论

当前结构适合继续完善，无需重做：普通演出以演出身份和时间为主，音乐节以艺人、舞台和下一场为主，锁屏与展开态复用内容层级。

**还不能判定为“所有情况下都符合用户习惯”。主要缺口是提醒对象的一致性、后台更新后的主现场一致性、计时语义、过期内容的可信度，以及提醒和多语言的一致性。**

本文的“符合习惯”是基于信息是否易懂、状态是否可信、交互是否符合系统惯例的设计判断，不是用户研究结果。当前显示由代码及字符串目录核对；示意图不是设备截图。本轮未操作真机、未改动产品代码或真实数据，也未对所有场景重新录屏。

## 1. 用户扫一眼需要得到什么

| 用户处境 | 第一优先信息 | 第二优先信息 | 不需要抢占注意力的信息 |
| --- | --- | --- | --- |
| 去普通演出的路上 | 哪场演出、几点开场 | 距离开场多久、场馆 | 完整日程、功能入口 |
| 普通演出进行中 | 演出正在进行 | 已开场多久、已填写的散场时刻 | 重复开场时间、大封面 |
| 音乐节现场 | 谁在演、在哪个舞台 | 本场时间、下一场 | 全部舞台阵容 |
| 场间移动 | 下一位艺人、舞台、开演时刻 | 距离开演多久 | 上一场的进度 |
| 想看的艺人快开演 | 谁、哪个舞台、几点 | 还有多久；是否另有想看场次 | 与提醒无关的头像或场次 |
| 推送没有及时到达 | 信息截至哪个计划时间 | 原计划开演时间、打开时刻表 | 看似仍然实时的演出状态 |
| 演出结束 | 当前跟踪已结束 | 演出名称 | 继续走动的计时、催促式操作 |

设计目标是减少开 App 的次数。锁屏承担完整判断，灵动岛常驻态只承担识别和关键变化；不能要求一个小圆环独立解释全部业务状态。

## 2. 四种显示表面的当前布局

| 表面 | 当前实际内容 | 判断 | 最小建议 |
| --- | --- | --- | --- |
| 灵动岛紧凑态左侧 | 现场模式用艺人头像；普通演出用封面；无封面用 App 图标 | 有现场识别价值；提醒头像可能与姓名不一致，见问题 1 | 保留头像，确保取自同一场次 |
| 灵动岛紧凑态右侧 | 现场正在演出为进度环；其他未结束状态为系统计时，普通进行中另有声波；结束态有“已散场”分支 | 进度环节制合理；裸计时无法明确区分“还剩”和“已过” | 以紧凑的状态标记区别等待与进行中；不要塞完整句子 |
| 灵动岛最小态 | 固定 14pt App 图标 | 能识别 App，但无法感知阶段变化；整枚 App 图标也不是 Apple 推荐的品牌呈现方式 [A1] | 随后改为无容器品牌标记或清晰状态图形；空间不足时保持简单 |
| 灵动岛展开态 | 内容集中在 bottom 区；普通演出为 54×72 封面及信息列，现场为 54pt 头像、状态、艺人、同时在演、下一场 | 内容顺序基本合理；没有必要为了占满区域增加信息 | 先解决信息正确性，再实测相机附近留白和长文本 |
| 锁屏卡片 | 普通演出为 72×96 封面及信息列；现场为 64pt 头像与进度环、艺人、同时在演、下一场；外边距 16pt | 适合扫读；普通封面略占空间，但没有足够证据要求重排 | 保留；长文案先保护状态、艺人、舞台及关键时间 |

补充边界：

- 当前没有对灵动岛 limited-width 环境单独降级。固定 44pt 计时宽度在受限空间里存在截断风险；这不是已确认的截图缺陷。Apple 对这类显示建议适配 28pt 圆形区域。[A1][A2]
- “已散场”的紧凑态分支不代表结束后应继续占岛。正式结束 Activity 后，岛会移除；锁屏可按产品设置继续保留结束摘要。[A1][A2]
- 当前 Widget 没有额外按钮。这个取舍合理；用户的主任务是看状态，点击进入相关页面即可。

## 3. 各种情况下，现在会显示什么

下表引号内为当前简体中文状态词；计时和示例名称仅用于说明。所谓“显示”，以 Activity 已创建、系统给予显示机会且相关状态已发布为前提。

| 场景 | 当前锁屏 / 展开态 | 当前紧凑态 | 是否符合习惯 |
| --- | --- | --- | --- |
| 普通演出尚未进入活动窗口 | 不创建可见活动；支持时可提前安排启动 | 无 | 合理，避免长期占用 |
| 普通演出即将开场 | 演出名、场馆、开场时刻；“距离开场 · 倒计时”；若填了散场时间也可能展示 | 封面 + 倒计时 | 基本合理；不应靠颜色解释倒计时 |
| 普通演出已开场，有散场时间 | 演出名、场馆、开散场时刻；“正在现场 · 正计时” | 封面 + 声波 + 正计时 | 有歧义：“正在现场”像用户位置状态；计时应明确为“已开场” |
| 普通演出已开场，未填散场时间 | 不展示虚构的具体散场时刻；仍显示正计时；内部用默认 4 小时作为生命周期兜底 | 同上 | 隐藏虚构散场时刻是对的；默认边界到达不能等同于真实散场 |
| 音乐节当天首场之前 | 演出 / 音乐节名称、时间、下一场一行；仍走普通布局 | 演出封面 + 倒计时 | 可接受；临近开演时，首位艺人应能在下一场行被识别 |
| 音乐节一场正在演 | “正在演出 · 舞台”，本场起止、艺人名、头像进度环、下一场 | 艺人头像 + 进度环 | 合理，谁在演比秒级计时更重要 |
| 多舞台同时在演 | 主艺人 + 一位“同时”艺人及舞台；更多并行场次不展示 | 仅主艺人 | 控制信息量合理；可以把“同时”明确为“同时在演”，但不必增加更多头像 |
| 用户切换主现场 | App 发布的状态可以反映手选艺人 | 可随本地状态更新 | 前台合理；云端后续计划未承接此选择，存在跳回风险，见问题 2 |
| 场间，仍有下一场 | 下一位艺人、头像、“下一场 · 舞台”、右上角“18:00 开场”；无第二条下一场 | 下一位头像 + 倒计时 | 合理；完整卡片当前没有大倒计时，不要把模型里的计时误认为已显示 |
| 单个想看场次进入开演前 15 分钟 | “快开始了”，主标题换为提醒艺人；现场布局右上角为开演时刻；仍可能保留下一场行 | 现场头像或封面 + 倒计时 | 提醒方向合理；头像、下一场及演出时间锚点存在错配 / 重复 |
| 同一时段多个想看场次进入提醒窗 | 只突出排序第一位提醒艺人；虽然生成了 `reminderSummary`，界面没有展示 | 只显示一个对象 | 不完整，用户看不出另有冲突场次 |
| 提醒窗口内遇到其他演出边界 | 每个仍标记提醒中的计划步骤都可能附带 alert | 同一提醒可能再次展开 / 响铃 | 不合理，状态持续不应等同于新提醒事件，见问题 1 |
| 提醒艺人正式开演 | 若收到新状态，退出提醒态并回到演出状态 | 切换为对应头像及进度 | 合理；推送缺失时不能承诺自动正确换场 |
| 一场结束，云端更新延迟 | 重新渲染时会检查旧场次结束；可能退回演出名称和“正在现场”，没有“更新待确认”提示 | 环形进度或计时取决于最后渲染状态 | 不充分，见问题 3 |
| 当天自然结束 / 普通演出到结束边界 | 最终态“已散场”，使用演出名；自然结束按代码保留约 15 分钟后移除 | 真正 end 后移除 | 已知散场边界下合理；音乐节单日结束可更准确地用“今日演出已结束” |
| 演出取消、用户提前结束、删除当前现场 | 走结束 / 移除路径，不设计额外确认卡片 | 移除 | 合理；不应把这些不同原因一律描述成“已散场” |
| 延期，未确定新日期 | 不继续展示原时间活动 | 无 | 合理，避免过期倒计时 |
| 延期有新日期 / 改时间或场馆 | App 同步后重新计算，必要时重建预约活动 | 随新状态变化 | 合理；App 尚未获知修改时，服务端旧计划仍可能继续，不能承诺即时纠正 |
| 多日音乐节，当日结束到次日之间 | 当日活动结束；未来活动是否安排受系统版本、下一次 App 同步及窗口约束 | 当日岛移除 | 符合每天有始有终的习惯；当前推送计划只覆盖本次活动截止时间 |
| 设备跨时区 / 跨午夜 | 时刻按演出时区格式化；时间行通常只显示钟点，不带“次日” | 短计时 | 演出时区合理；23:00–01:00 的日期关系仍需明确 |
| 无头像 / 无封面 | 艺人用首字符占位，封面尽量回退 App 图标；不新增错误提示 | 头像占位或 App 图标 | 合理，不需要暴露缓存或网络错误 |
| 关闭实时活动、无可用 token、上传失败 | 活动显示及提醒接管取决于各自条件；上传失败时服务侧保持本地通知兜底 | 不保证有岛 | 合理；“本地兜底”不等于已交给云端后断网仍保证收到提醒 |
| 用户手动移除活动 | 系统移除活动；演出本身不应因此结束 | 无 | 应遵循系统习惯；是否被后续 App 同步重新创建需单独验收，本文未确认 |

活动窗口当前为：开场前 30 分钟与“结束前最多 8 小时”两者取较晚时刻。长于 8 小时的音乐节可能开演后才进入可见窗口，这是当前策略，不应向用户承诺从首场起全程常驻。

## 4. 最值得处理的五组问题

### 1）提醒内容没有绑定同一个完整事件 —— 优先修改

**观察**

提醒主标题来自 `reminderArtistName`，现场提醒头像却来自 `nextArtistImageFilename`；`next` 也继续使用普通下一场。提醒对象不一定是最近的一场，例如 18:00 的想看艺人 A 进入提醒窗时，17:50 还有非想看艺人 B。

此时可能出现“A 的名字 + B 的头像”，或者主标题和下一场行重复 A。首场之前若走普通布局，主标题已经变成提醒艺人，元数据却仍锚定整场活动的开散场时间。

多个提醒虽然生成摘要及场次 ID，界面和云端 alert 都没有消费摘要。服务端又把“提醒状态仍有效”的每一步都视为可响铃提醒。

**为什么影响用户**

提醒要帮助用户决定往哪个舞台走。身份错配会指错对象；遗漏并行想看场次会隐藏冲突；重复声音会增加打扰。

**最小改动**

使提醒标题、头像、舞台、开演时刻来自同一个 performance；提醒与普通下一场相同时去掉重复行。多个提醒时增加一条“另有 1 场想看即将开演”，点击进入时刻表看完整冲突；不要把所有姓名塞进标题。

以场次和开演时间区分提醒事件。同一事件持续期间的内容更新保持静默，只有首次需要用户注意时附带 alert；换计划版本也不应重新提醒同一事件。

**可复核的推演**

A 18:00 开演、已想看；17:45 首次提醒；17:50 另一个场次结束触发新步骤。两个步骤的 `isReminderActive` 都可为 true，当前服务端没有事件去重判断，因此都可能带声音。此处是代码路径推演，未做本轮真机重复响铃复现。

**证据**：[C1] 的提醒分支，[C3] 的 `activeReminder`，[C6] 的提醒字段映射及投递判断。

### 2）后台更新与用户刚选择的现场不一致 —— 优先修改

**观察**

本地发布传入 `focusedPerformanceID` 和艺人图片解析函数。云端计划构造没有接收手选主现场；协调器也没有向 builder 传艺人图片解析函数，后者默认返回 nil。

**为什么影响用户**

用户在 App 选了 B 舞台后，后续云端步骤可能重新按默认优先级选 A；头像字段也可能被没有图片的状态覆盖。看起来像 App 忘记了选择，或头像突然丢失。

**最小改动**

本地状态和本次云端计划使用相同的主现场选择与已缓存图片映射。手选场次仍在演出时维持选择，结束后才按现有排序规则选下一位；无需新增一个面向用户的设置。

这是代码路径确认的一致性缺口。具体哪次推送会覆盖画面，仍需运行时录屏验证。

**证据**：[C4] 的 `publish`，[C5] 的协调器及计划 builder。

### 3）过期与预计结束被当成确定的现场事实 —— 优先修改

**观察**

`contentExpirationDate` 已用于单场结束、下一场开演等边界；显示层的 `isStale` 主要影响声波，没有明确“信息待更新”文案。跨边界的新状态仍依赖 App 或 APNs 发布；系统计时自行变化不等于系统会自行换艺人。

等待阶段使用 `Text(date, style: .timer)`，没有以目标时刻为上界的倒计时区间；目标过去后存在继续计时的语义风险。即使某次重新渲染按 `now` 降级，也不能依赖秒级自动重算整个内容分支。

未填写散场时间时，内部默认 4 小时边界最终仍能生成“已散场”。这只是跟踪生命周期，并不是主办方确认散场。

**为什么影响用户**

旧时间配“正在演出”会显得比实际更确定；“快开始了”旁边一个重新增长的计时也无法解释。演出还在继续时出现“已散场”，会直接损害可信度。

**最小改动**

正常状态保持简短。只有过期时降为“信息待更新”，显示原计划艺人、舞台和时间，收起实时声波；不要把断网简单判断成散场。等待计时到目标归零，不能变成无标签正计时。

确认的结束使用“已散场”或“今日演出已结束”；仅内部兜底时间到达时安静结束跟踪，必要的结束摘要用“本次跟踪已结束”。不要求用户再确认。

**证据**：[C1] 的 `showsWave`、计时组件，[C2] 的 `staleDate`、`hasEnded`，[C3] 的普通演出兜底及最终态。Apple 对 stale 的定义是内容已过期，不能把它当作业务结束事实。[A2][A3]

### 4）时间文案与语言切换不够一致 —— 随后修改

**观察**

普通进行中显示“正在现场 · 计时”；内容模型虽有“已开场” caption，当前视图没有显示它。云端提醒标题和正文为中文固定拼接，没有语言信息。Widget 英文还存在 `%@ opening`、`%@ ends`，与 App 中的 `Starts at %@` 不一致。

**为什么影响用户**

“正在现场”容易读成位置判断；裸时间缺少方向。英文用户可能看到中文云端提醒，且切换本地 / 云端提醒后信息量不同。

**最小改动**

普通进行中使用“已开场 42 分钟”或“演出进行中 · 已开场 42 分钟”。提醒优先给绝对开演时刻，避免延迟送达后仍写“还有 15 分钟”。统一 App 与 Widget 的英文表达；提醒文案按用户选择语言生成，沿用 i18n 机制。

完整卡片保留“次日”提示；紧凑态不增加日期长句。英文长标题优先截断演出名，不能挤掉状态、舞台及关键时间。

**证据**：[C1]、[C6]、[C7]。

### 5）点击后的去向没有显式对应当前内容 —— 随后修改

**观察**

当前 `ShowLiveActivity` 未配置与当前现场身份关联的 `widgetURL` 或内容链接。系统可以启动 App，但代码没有保证把用户送到这张卡片对应的页面。

**为什么影响用户**

卡片在提醒某个舞台时，点击后仍可能停留上次打开的其他页面，用户需要重新寻找。

**最小改动**

普通演出点击进入该现场；音乐节和想看提醒进入对应时刻表 / 当前现场上下文。复用既有深链规则，紧凑态两端保持同一目的地，不新增确认弹窗。

缺少显式链接是代码事实；每种 App 冷热启动情况下目前落在哪里，仍需实际点击验证。

**证据**：[C8]、[C9]；符合 Apple 让点击直接进入相关内容的建议。[A1][A2]

## 5. 建议定稿的文案

以下均为建议，尚未写入产品。`18:00` 等是示例；中英文必须绑定同一场次及其演出时区。繁体应同步进入现有 String Catalog。

| 状态 / 元素 | 简体中文建议 | 英文建议 | 使用位置 |
| --- | --- | --- | --- |
| 开场前 | 距离开场 | Starts in | 卡片状态，与倒计时相邻 |
| 开演时刻 | 18:00 开场 | Starts at 18:00 | 完整卡片时间锚点 |
| 普通演出进行中 | 已开场 42 分钟 | Started 42 min ago | 卡片状态行，替换无标签正计时 |
| 现场正在演出 | 正在演出 · 主舞台 | Now playing · Main Stage | 现场状态行 |
| 并行演出 | 同时在演 | Also playing | 另一位艺人前 |
| 场间 | 下一场 · 主舞台 | Up next · Main Stage | 下一场主标题上方 |
| 想看提醒 | 想看的演出快开始了 | Your saved set starts soon | 完整卡片；窄空间可保留“快开始了” / “Starting soon” |

## 6. 布局示意与取舍

以下是建议结构，不是当前画面的截图。正式实现继续复用现有 `WidgetTheme`。

### 普通演出：开场前 / 进行中

```text
[演出封面]  周末巡演
            Livehouse · 18:00 开场
            距离开场 12:34

[演出封面]  周末巡演
            Livehouse · 预计 22:00 散场
            已开场 42 分钟
```

延续当前封面与信息列。开场后无需继续用完整开场时刻挤占主状态；有足够空间时保留即可。结束时删掉计时，降低高度，无需增加“去记录”等第二个主任务。

### 音乐节：正在演出

```text
[头像/进度环]  正在演出 · 主舞台       17:00–17:40
              落日飞车
              同时在演 另一乐队 · 风舞台
------------------------------------------------
18:00  [头像] 椅子乐团  [想看心形]  风舞台
```

这与当前结构接近，保留即可。最多一位并行艺人和一条下一场，完整冲突留给时刻表；舞台不能只靠颜色识别。

### 想看提醒：对象优先

```text
[提醒艺人头像]  快开始了 · 风舞台       18:00 开场
               椅子乐团
               另有 1 场想看即将开演
```

提醒对象与下一场相同时，不再重复下一场行。没有匹配头像就显示该提醒艺人的首字符，不能借用另一位艺人的图片。若提醒对象不是下一场，空间允许时仍可在底部保留那一条不同的下一场。

### 过期：明确降低确定性

```text
[艺人头像]  信息待更新
            椅子乐团 · 风舞台
            原定 18:00 开演
```

不增加弹窗，也不每秒提示“正在重试”。正常更新到达后回归正常内容。灵动岛窄空间优先显示可识别的状态图形，完整解释放在展开 / 锁屏。

## 7. 不建议改的地方

- 保留一个当前现场活动，避免为每个舞台创建多个互相竞争的活动。
- 保留现场模式“艺人优先、舞台其次、下一场一行”的层级，不重新变成大倒计时主导。
- 保留系统时间驱动的计时与进度；不为数字变化每秒发推送。
- 保留无图片时的安静占位，不在活动卡片暴露下载状态。
- 保留自然结束后短暂展示摘要的方式；不要把“离岛”与“锁屏立刻消失”绑定成一回事。
- 不增加装饰性动画、复杂快捷操作或完成后确认。App 内换场动画与 ActivityKit 内容更新是两个表面，不能用前者的录屏代替后者验收。
- 本文不增加大字号适配或 VoiceOver 工作项；长文本及常规中英文显示仍需验收。

## 8. 修改顺序与验收

建议先解决内容和状态正确性，再做文案及窄空间收敛：

1. 提醒事件一致性：同一艺人、头像、舞台和时刻；多场摘要；同一事件只提醒一次。
2. 前后台一致性：手选主现场与已缓存头像进入云端计划。
3. 过期及生命周期语义：等待计时不反向、过期不冒充实时、兜底截止不冒充散场。
4. 文案及多语言：明确计时方向；本地和云端同一语言、同一时间语义。
5. 点击去向、limited-width 及视觉细节：以实际设备画面决定是否调整字号和间距。

| 验收组合 | 合格标准 | 验证方式 |
| --- | --- | --- |
| 普通演出开场前 → 进行中 → 结束 | 计时方向清楚，状态不滞留，结束后离岛，锁屏仅保留摘要 | iPhone 18 Pro 模拟器录屏，覆盖展开 / 紧凑 / 锁屏 |
| 未填散场时间 | 不展示虚构散场时刻，内部截止不宣称真实散场 | 固定时间的内容验证及最终卡片截图 |
| A 正在演、B 最近开演、C 是提醒对象 | 提醒主标题和图片均为 C，舞台和时刻一致 | 构造三场快照；锁屏与岛展开态截图 |
| 同一提醒窗有多次演出边界 | 同一提醒事件只响一次，卡片可继续静默更新 | 测试计划逐步投递；真机录屏和投递日志 |
| 同时有两个想看提醒 | 主对象稳定，能看出另有场次；正文不溢出 | 两种开演时间组合、同一开演时间组合 |
| 手动选 B 舞台后退后台 | 后续推送不跳回 A；头像不无故变成占位 | 选主现场、终止隔离测试 App 宿主、云端推送验证 |
| 推送跨过开演 / 单场结束边界仍未到达 | 不出现反向等待计时，不把旧场次称为仍在演 | 控制投递延迟；跨边界锁屏录屏 |
| 冷启动 / 热启动点击卡片 | 到达同一现场或对应时刻表，不弹第二次确认 | 从其他 tab、App 未运行两种状态点击 |
| 简中 / 繁中 / 英文、长艺人及舞台名 | 状态和关键时刻保留；文案语言一致；不挤掉舞台 | 各语言截图；英文同时核对云端 alert |
| 23:00–次日 01:00、设备与演出时区不同 | 时刻归属正确，跨日关系清楚 | 指定演出时区的快照与设备截图 |
| 电话 / 其他活动竞争、横屏 | compact / minimal / limited-width 能识别且不截断关键信息 | 模拟器可覆盖部分；iPhone 16 Pro 真机补验 |
| 常亮屏降低亮度、浅色 / 深色壁纸、StandBy | 状态与关键文字可读，缩放后图片可用 | 真机视觉验收；当前未验证 |
| 无灵动岛设备 | 锁屏卡片及提醒横幅信息完整 | 相应模拟器截图 |

真机继续使用隔离测试 App 和虚构演出；不覆盖用户正式 App，不修改正式本地 / iCloud 演出数据。录屏与测试日志保留在 Git 外。

## 10. 修复落实与自动化验证状态（2026-10-21）

针对第 4 节指出的 5 组核心缺口，已在代码层完成端云闭环修复并补齐自动化测试：

1. **提醒内容与头像统一（问题 1）**：
   - `ShowLiveActivityAttributes.swift` 补充 `reminderArtistImageFilename` 与 `reminderCount`，严格向前兼容；`LiveActivityPlanner.swift` 中的 `activeReminder` 带出 `performanceID`，提醒头像绑定目标艺人，消除“A 的名字 + B 的头像”错配。
   - 提醒对象与下一场相同时自动去重；多场想看提醒时展示“另有 N 场想看即将开演”（支持 en/zh-Hans/zh-Hant 多语言复数处理）。
   - 服务端（`liveActivityReminder.js` / `dispatchLiveActivityPush/entry.js`）以场次与开演时刻绑定 `reminderKey`，建立 `deliveredReminderKeys` 收据机制，换计划版本或步骤跨越时不重复带声音打扰。
2. **端云主现场手选与头像一致（问题 2）**：
   - `LiveActivityPushCoordinator.swift` 接收并保持 `focusedPerformanceID` 与 `artistImageFilename` 头像解析闭包，云端后续步骤不再意外回退默认舞台或丢失头像。
3. **计时语义与过期真实性（问题 3）**：
   - 倒计时由开放式 `Text(style: .timer)` 改为以目标为上界的系统倒计时 `Text(timerInterval: ..., countsDown: true)`，到达目标后停留在 00:00，不再反向变成无标签正计时。
   - `isStale` 时不冒充实时进行，明确降级为“信息待更新”，保留原定演出信息并收起声波；紧凑态右侧显示警告图标；区分单日结束“今日演出已结束”、确认散场“已散场”与内部 4 小时兜底“本次跟踪已结束”。
4. **文案规范与国际化统一（问题 4）**：
   - 普通进行中明确标为“已开场”；跨午夜散场提示“预计次日 %@ 散场”；云端推送同步携带客户端语言偏好生成多语言 alert；完善 App 与 Widget 的 String Catalog 翻译。
5. **卡片点击显式深链（问题 5）**：
   - 锁屏横幅与灵动岛展开态挂载 `.widgetURL(BeforeShowOpenURL.make(...))`，现场模式与提醒态直达对应时刻表，普通演出直达该现场，打通 `NotificationDeepLinkRouter` 闭环。
