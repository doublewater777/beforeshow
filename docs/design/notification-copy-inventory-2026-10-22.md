# 开场前 BeforeShow：通知文案全量汇总

供没有项目上下文的评审者使用。快照日期：2026-10-22。

这是**当前工作区代码**的简中文案，不等于 App Store 已发布版本。包含独立听歌提醒及全部排程节点，已按外部评审和节点 9 的最终确认稿更新。

## 产品与阅读背景

开场前是一款演唱会、音乐节的现场陪伴 App。用户添加想去的现场，可查看路线、管理时刻表和想看艺人、邀请同行、听歌，以及在散场后记录记忆和查看足迹。

- 大部分提醒：标题是简短状态；正文第一行是完整现场名，第二行是消息。以下用 `【现场名】` 表示实际名称，换行也是当前代码真实结构。
- 前一天提醒：最近已改为现场名作标题，正文不再重复现场名。
- 艺人开演提醒：标题直接使用艺人名，正文给时间和舞台。
- `【开场时间】`、`【场馆】` 等为动态值，并非用户会看到的占位符。缺失信息时使用下列对应变体，不会显示空占位符。
- 所有固定时刻按现场时区。准备期和散场后节点主要围绕用户的当前现场；其他现场仍可收到开场前三小时提醒。
- 这些不是用户必然全部收到的通知：用过的功能、推荐资格、散场状态、通知权限、添加时间及当前现场选择都会影响发送。
- 「记忆碎片」是照片/记忆记录功能；「足迹」是过去现场的归档；「想看」是用户主动标记的艺人场次。

## 一、当前排程会生成的提醒

### 1. 准备期：同行

触发：通常开场前 7 天 20:00；需要有可推荐的同行功能。当前规则去掉了通知推荐候选里的听歌，因此此节点不会用听歌兜底。准备期功能推荐最多一条；开场前 7 天后才添加的现场不追补此节点。

标题：

> 准备这场

正文：

```text
【现场名】
还有 7 天。和朋友一起去？邀请他们加入这场。
```

去向：同行功能。

### 2. 准备期：时刻表

触发：开场前 7 天的推荐时刻已过、前 3 天的时刻尚未过时添加现场，可在前 3 天 20:00 推荐；当前仅音乐节有此候选。没有合适候选则不发，不是每场必发。

标题：

> 准备这场

正文：

```text
【现场名】
还有 3 天。把时刻表存进这里，在现场能随时查看。
```

去向：时刻表。

### 3. 开场前一天

触发：前一天 20:00。

标题：

> 【现场名】

正文第一句为「明天开场。」；多日现场为「明天开始。」，不再播报具体时刻。第二句按目标区分：

- 大合唱：「挑几首常演的热门歌预热一下。」
- 想看节目：「听听你标记的那些艺人吧。」
- 无目标唱片，有唯一艺人：「听听【艺人名】的歌。」
- 无目标唱片，无唯一艺人：「先听听这场的歌吧。」

目标唱片：单艺人优先大合唱；多艺人优先想看节目，兜底大合唱。

去向：听/唱片详情。带音乐目标时有系统动作「播放」。正文点击不自动播放。

### 4. 音乐节当天早上

触发：当天 09:00。只针对音乐节；已开场或与早场的前三小时提醒过近时不单发。

标题：

> 今天开场

正文：

```text
【现场名】
今天【开场时间】开场 · 【场馆或城市】。看看时刻表，确认想看的艺人场次。
```

信息不足时第一句的完整变体：

- 有时间，无地点：「今天【开场时间】开场。」
- 无时间，有地点：「今天开场 · 【场馆或城市】。」
- 均无：「今天开场。」

去向：时刻表。

### 5. 开场前三小时

触发：开场前三小时，各现场均可收到。临时添加、已进入前三小时的现场使用下一节的补发文案。

标题：

> 快开场了

正文：

```text
【现场名】
【开场时间】开场 · 【场馆或城市】。还有 3 小时，准备出门。
```

当前现场有目标唱片时，末句为「还有 3 小时，准备出门，路上让这些歌陪你出发。」；不显示具体唱片名。

信息不足时：无地点就省略「 · 地点」；没有确定开场时间的日期型现场在当天 12:00 生成提醒，正文开头使用「今天开场」。

去向：正文仍是路线；非当前现场按跨现场路由处理，不改变持久化当前现场选择。带音乐目标时另有「播放」动作。

### 6. 临时添加、临近开场补发

触发：添加时距离开场不足三小时、且尚未开场，安排在约 10 分钟后，最晚不超过开场时刻。正文按触发时刻距离开场的剩余时长生成。

标题：

> 快开场了

正文两种：

```text
【现场名】
【N】小时后开场 · 【场馆或城市】。别错过开场。
```

```text
【现场名】
【N】分钟后开场 · 【场馆或城市】。别错过开场。
```

无地点则省略地点。不追加听歌句，不提供「播放」动作。

去向：路线。

### 7. 想看艺人即将开演：本地通知

触发：用户标记想看的艺人场次，开演前 15 分钟。提醒使用绝对开演时间，不固定写「还有 15 分钟」。

标题：

> 【艺人名】 快开始了

正文：

```text
【开演时间】开演 · 【舞台名】
```

例如：

```text
标题：椅子乐团 快开始了
正文：18:00 开演 · 风舞台
```

去向：时刻表。

### 8. 想看艺人即将开演：实时活动远程提醒

同一提醒也可能由实时活动远程链路承接，不意味着本地、远程两条设计为重复发送。

标题：

> 【艺人名】 快开始了

正文：

```text
【开演时间】开演 · 【舞台名】
```

有多个同时需要提醒的想看场次时追加：

```text
【开演时间】开演 · 【舞台名】 · 另有【N】场想看即将开演
```

N 不包括标题中的第一场。缺时间或舞台就省略相应片段；没有艺人名时兜底现场名。本地和远程标题均在艺人名后保留一个半角空格。

### 9. 散场后十五分钟

触发：整场预计散场或用户确认散场后 15 分钟；多日现场以最后一天为准。已完成散场仪式则不再排此节点。此条为被动通知，不响铃。

标题：

> 散场后

尚未确认散场：

```text
【现场名】
散场了吗？记下时间，聊聊这场怎么样。
```

已确认散场：

```text
【现场名】
散场了，记下这一刻。
```

去向：散场仪式；未确认散场时先确认散场时间。

### 10. 散场次日回看

触发：散场次日 11:00。优先按确认散场时间，否则按最后一天的估算日期；已完成散场仪式不再排此节点。

标题：

> 回看这场

尚未确认散场：

```text
【现场名】
这场几点散场？记下时间，也可以留一句感受。
```

已确认散场：

```text
【现场名】
这场结束了，留下一点记忆。
```

去向：散场仪式。

### 11. 确认散场后第三天：足迹 / 下一场

触发：已确认散场后的第三天 20:00，有可推荐功能时发一条。候选顺序先足迹，再下一场/添加现场，不是每种文案各发一条。

标题统一为：

> 回看这场

足迹候选：

```text
【现场名】
已收进足迹，可以生成一张卡片留念。
```

有下一场现场，且轮到下一场候选：

```text
【现场名】
这场已收进足迹。下一场是【下一场名称】，还有【N】天。
```

没有下一场，且轮到添加候选：

```text
【现场名】
这场已收进足迹。有新的演出计划了吗？可以记下下一场。
```

去向分别为足迹、下一场、添加现场。

### 12. 独立听歌提醒

标题统一为完整现场名，正文不重复现场名，不播报倒计时。正文打开唱片详情，系统动作「播放」直接装入目标播放；无缓存时按艺人回退。

| 目标 | 正文 |
| --- | --- |
| 大合唱 | 收录了现场常演的热门歌，可以先熟悉一下。 |
| 专辑 | 听听【艺人名】的专辑《【专辑名】》。 |
| 艺人兜底 | 来听听【艺人名】的歌。 |
| 精选歌单 | 从这份精选歌单开始，认识一下【艺人名】。 |
| 新歌合辑 | 听听参演艺人最近发行的新歌。 |
| 深挖合辑 | 热门曲目之外，这些作品也值得一听。 |
| 队列用完后循环大合唱 | 离现场越来越近了，再听听这份热门歌单吧。 |

## 二、已移除的未发送分支

本次清理已删除开场时记忆提醒、普通现场早晨路线提醒、第三天未确认散场兜底，以及旧小组件/听歌/记忆碎片通知候选文案。添加后次日与前十四天的推荐槽位也已移除，不再作为待评审文案。

`addedFollowUp`、`fourteenDaysBefore`、`openingMemory` 三个已发布的节点 raw value 仅为识别旧持久化记录保留，不生成新通知、不提供旧文案。共享首页推荐与旧通知深链仍兼容。

## 三、附录：实时活动上的提醒与状态文字

这些是锁屏/灵动岛活动中的状态展示，**不是额外一轮推送通知**。

| 状态 | 当前文字与信息结构 |
| --- | --- |
| 尚未开场 | 「距离开场」＋现场名＋「【时间】开场 · 【场馆】」＋倒计时 |
| 想看艺人即将开演 | 「快开始了」＋艺人名＋「【舞台】 · 【时间】开演」；多场时有「另有【N】场想看即将开演」 |
| 艺人正在演出 | 「正在演出」＋艺人名＋「【舞台】 · 【时间】结束」；另有「已开场」、演出时间段和进度 |
| 音乐节场间 | 「下一场」＋艺人名＋舞台和开演时间 |
| 普通现场进行中 | 「已开场」＋现场名＋预计散场时间或场馆 |
| 有散场时间的结束状态 | 「已散场」＋现场名、场馆 |
| 音乐节日程结束 | 「今日演出已结束」＋现场名、场馆 |
| 仅结束本次跟踪 | 「本次跟踪已结束」＋现场名、场馆 |

预计结束时间的变体还包括「预计【时间】散场」「预计次日【时间】散场」，跨更远日期时使用日期和时间。

## 四、建议评审问题

1. 每条通知能否独立看懂？标题与正文是否重复，缺少上下文还是信息过密？
2. 「准备这场」「回看这场」「现场」「艺人」等用词是否一致、清楚？
3. 时刻表保存邀请是否清楚，是否与导入入口一致？
4. 散场状态未确认时的问句是否自然，几次提醒是否显得催促？
5. 「已收进足迹」「生成一张卡片留念」是否与用户点开后的结果一致？
6. 开场提醒是否应该同时承载听歌邀请？紧急程度与语气是否匹配？
7. 本地与远程想看提醒是否应该保持完全一致的文字？
8. 听歌通知的新草稿，如何延续以上语气，同时避免任务感、营销感和虚假的演出曲目承诺？

请将规范要求、产品事实、个人审美判断分开，不要因为表内列出多个分支就假设用户会连续收到所有分支。
